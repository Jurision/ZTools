# 微信语音与主搜索框兼容性排查（2026-11-12）

## 已验证

- 本机微信输入法为 3.0.2.36，ZTools 运行 release 20261112-090143。
- 使用临时 profile、假 Everything、隐藏源码 Electron 窗口，通过 Chromium 调试协议模拟连续 IME 组字、父级更新和最终提交，输入文字均保留。测试不调用真实语音服务、不读取系统剪贴板、不抢前台。
- 用户对照一：键盘 Ctrl+Space 打开 ZTools，鼠标后退侧键开始和结束语音，文字直接提交，没有“已复制”提示。
- 用户对照二：中键通过 SmartCopyPaste 开始语音，后退侧键结束，文字直接提交，没有“已复制”提示。
- 第二组观察期间记录到两次 ZTools 前台语音面板开关循环，系统剪贴板序号始终为 636。只记录窗口身份、可见性及剪贴板序号/所属进程，没有读取语音、搜索文本或剪贴板内容。
- 用户报告中键开始、中键结束时会出现“已复制，粘贴即可使用”，此前已观察到由 SmartCopyPaste 发送结束快捷键。

## 判断和边界

问题已缩小到中键结束路径，不支持“ZTools 搜索框只能用剪贴板接收语音”的结论。Chromium 隔离测试不能替代真实 Windows TSF/微信输入法端到端测试，但两次用户对照证明本机能直接提交。

中键结束路径包含额外的 Ctrl+Shift+F11，再由辅助程序模拟左 Ctrl+左 Win+A；后退侧键直接发送后者。这两个差异尚未完全分离，不能断言已经证明是 F11 或模拟按键中的某一个导致。

ZTools 的 Esc 默认会清空文字或隐藏主框，因此辅助程序不得再用 Esc 结束语音。不得通过清空、恢复剪贴板掩盖问题：既有历史记录仍可能留下，且可能影响其他复制操作。

## 后续最小验证

先在用户配合的短暂语音测试中，仅向辅助程序发送内部结束请求，不向 Windows 投递 Ctrl+Shift+F11，检查原生语音结束是否直接提交；不读取剪贴板内容，只比较序号。

若该对照成功，可考虑把 ATK 中键恢复为标准鼠标中键，由辅助程序仅拦截中键并触发内部请求，其他鼠标事件全部透传。该方案尚未实施，需验证原有前进侧键复制粘贴、后退侧键语音、左右键、滚轮及焦点切换。

本轮仅增加回归诊断用例和文档，未修改生产搜索逻辑或运行中的辅助程序，未部署新版本。
